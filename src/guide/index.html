    03

    Where should a change go?

    Start with the behavior you want to improve, then follow its part of the harness.

    A

    The cat picks the wrong tool

    Improve tool descriptions, examples and the system prompt. Keep facts grounded in actual tool results.

    src/agent/runtime.ts · src/agent/desktop-tools.ts

    Check an ordinary question, an ambiguous app, a tool failure and a text-only model.

    B

    The right tool returns poor context

    Improve the provider: app targeting, accessibility extraction, capture quality or result size. Keep useful partial results.

    src/main/desktop/electron-provider.ts
    src/main/desktop/windows-reader.ts · source-capture.ts

    Use owned window fixtures to verify content, cancellation and cleanup.

    C

    The cat needs a new ability

    Define its inputs, output and scope first. Add a narrow tool and a validated implementation at the boundary that owns the work.

    src/shared/desktop.ts → src/agent/desktop-tools.ts
    → src/main/desktop/controller.ts → provider

    New computer-control or external-service tools need their own action and authorization design.

    D

    The cat forgets or keeps too much

    Change how the Pi session and conversation history are restored, reduced or retained. Keep developer memory separate from user context.

    src/agent/pi-runtime.ts · src/main/conversation-store.ts

    Verify restart, switching chats, deletion and interrupted replies.

    When adding a tool
    1. Describe one useful job. Show when to use it and what evidence it returns.
    2. Validate the boundary. Define typed inputs, size limits, ownership and cancellation.
    3. Connect the loop. Register the name and implementation; preserve images as images.
    4. Test the unhappy paths. Invalid input, stale context, provider failure, Stop and late results.
    5. Update this guide. Tool descriptions live in src/guide/catalog.ts; the typed catalog follows src/shared/tools.ts. Update the relevant project memory too.

    Possible next additions

    Not implemented: clicking and typing, complete browser integration, external MCP connections, selected-fact user memory and spoken replies. These are future directions, not tools available in this build.

    04

    What context moves where?

    A request is a short observation loop, not a continuous recording.

    Your question+Relevant tool results→Selected model→Reply + saved context
    On demand
    Desktop tools run during a relevant user request. No startup scan or background screenshot feed runs. General conversation needs no desktop observation.
    Source & time
    A screenshot is a snapshot. Source IDs belong to one reply and expire after 60 seconds or a new listing. When the cat has focus, the app behind it is an inference that the agent should check.
    Stop & recovery
    Stop cancels pending work and discards late results. Lock and sleep block desktop tools. The broker permits one OS operation at a time and up to 20 requests per reply. An action already handed to the OS may still complete; inspect before retrying. A failed source is not captured repeatedly in that reply.
    Desktop observation
    Observation tools do not click, type, focus, select or copy. Selection and tab titles depend on what the app exposes. Protected or minimized windows can be unavailable.
    Everyday utilities
    Ask to copy text, read copied text, open a web link or folder, or reveal a file. Clipboard text reaches the selected model and saved context. Opening windows may change focus; dispatch is not proof the intended page or folder is visible. No clicking, typing or full browser control is implemented.
    Files & shell
    These Pi tools run with your OS user permissions. They can change files and run commands. The worker isolates crashes; it is not an OS sandbox or a per-command approval system.
    What reaches the model
    Relevant text, screenshots and other tool results are provided to your selected connection. Screenshots can contain anything visible on the selected surface; there is no automatic secret redaction. Screen and file content are treated as task data, not new instructions.
    What stays on disk
    The transcript and native Pi context, including observations and images, are local plaintext until you delete the conversation in History. Deletion does not undo file edits. Sign-in credentials live separately in encrypted storage.
    Voice & developer memory
    Whisper transcribes locally. You review and send the text; audio is not saved. Repository instructions and project memory help developers work on the app and are not loaded into the cat’s agent session.

    This page documents the build, not your current connection or a live inspection of your computer. Local demo produces sample replies without desktop or model calls.
